# 第6章 Verification Projects

## 実証プロジェクト戦略

---

# 6.1 Purpose

BaseKitは、机上の設計のみでCoreを成長させることを目的としない。

実際のシステム開発を通じて得られた知見を基に、再利用可能な共通機能を抽出し、CoreおよびPluginへ反映する。

本章では、BaseKitを成長させるための実証プロジェクトの考え方と運用方針を定義する。

---

# 6.2 Basic Principle

BaseKitは「実証による設計」を基本原則とする。

新しいアイデアは、最初からCoreへ組み込まない。

まず実証プロジェクトで検証し、十分な有効性が確認されたものだけを共通資産として採用する。

実証プロジェクトは、BaseKitを育てるための実験場である。

---

# 6.3 Objectives

実証プロジェクトの目的は以下とする。

* Core候補となる共通機能の発見
* Pluginアーキテクチャの妥当性検証
* SDKの改善
* Architectureの改善
* AIとの共同開発手法の改善
* ドキュメントの改善
* 開発効率の検証

完成したアプリケーションを作ることではなく、BaseKitを改善することを第一の目的とする。

---

# 6.4 Project Selection Criteria

実証プロジェクトは、以下の条件を満たすものを優先する。

* 業務システムとして実用性がある
* 他分野への応用が期待できる
* 共通機能を多く含む
* Pluginとして独立しやすい
* AIとの共同開発に適している

---

# 6.6 Pilot Project

最初の利用者は、身近な環境から開始する。

想定する初期利用者

* 開発者自身
* 家族
* 知人
* 小規模事業者
* 個人事業主

小規模なフィードバックを重ねながら改善を進める。

---

# 6.7 Feedback Cycle

すべての実証プロジェクトは、以下のサイクルで改善する。

```text
開発

↓

利用

↓

フィードバック

↓

課題整理

↓

Blueprint更新（必要に応じて）

↓

Architecture更新

↓

Specification更新

↓

Core／Plugin改善

↓

再検証
```

改善は一度で完了させず、継続的に繰り返す。

---

# 6.8 Promotion Criteria

実証プロジェクトで得られた成果をCoreへ反映する条件を定義する。

以下をすべて満たした場合に、Coreへの統合を検討する。

* 複数プロジェクトで利用された
* Rule of Threeを満たした
* Pluginとして十分に成熟した
* 後方互換性を維持できる
* Architectureと整合している
* Specificationが整備されている
* AIレビューおよび人によるレビューを完了している

---

# 6.9 Success Metrics

実証プロジェクトでは、以下を評価する。

* 共通化できた機能数
* 新規Plugin作成時間
* Core変更回数
* Plugin再利用率
* AI実装率
* AIレビュー率
* ドキュメント整備率
* バグ修正時間
* 利用者からの改善提案数

これらを継続的に記録し、BaseKit改善の判断材料とする。

---

# 6.10 Version Evolution

BaseKitは実証結果を基に進化する。

```text
Idea

↓

Prototype

↓

Verification Project

↓

Reusable Plugin

↓

Core Candidate

↓

Core Component

↓

Stable Release
```

すべての機能は、この段階を経て成熟する。

---

# 6.11 Long-term Strategy

BaseKitは、単一の業務システムを開発するプロジェクトではない。

多様な実証プロジェクトを通じて共通基盤を育て、Pluginエコシステムを形成することを長期目標とする。

Coreは安定性を重視し、Pluginは自由な発展を促進する。

---

# 第6章まとめ

実証プロジェクトは、BaseKitを成長させるための中核的な活動である。

新しい機能はまずPluginとして実装し、実際の利用を通じて価値を検証する。

実証された共通機能のみをCoreへ取り込み、継続的な改善を繰り返すことで、長期的に保守可能で拡張性の高いOSS基盤を構築する。
