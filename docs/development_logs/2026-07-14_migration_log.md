## 1. 方針転換の背景と課題認識

### 課題：既存の「ERP的フルパッケージ」の限界
当初、プロジェクトは「顧客・見積・売上・仕入・在庫・決済」の6プラグインからなる統合ERPを志向していた。しかし、以下の実務的ペインポイントが浮き彫りとなった。
1.  **導入ハードルの高さ**: 組織の業務フロー全体を合わせる必要があり、導入の決定が重い。
2.  **セキュリティ規約への抵触**: 社用PCにおいて「野良ローカルサーバーの常駐」や「RDB（PostgreSQL）の勝手なインストール」が禁止されているケースが多く、個人業務効率化ツールが使えない。

### 解決策：4つのキラーツールへのフォーカスと「スタンドアロン版」の創設
ターゲットを「副業者・個人開発者」にシャープに絞り込み、以下の4つを公式公開アセットに選定した。
1.  **個人業務効率化ツール（通常Web版）**
2.  **個人業務効率化ツール（スタンドアロン版）**: サーバー・DBを必要とせずブラウザ単体で動く。
3.  **業務用SNSシステム**
4.  **複式簿記システム**

## 2. 主要な設計合意（3大防衛設計）

「Codex for OSS（OSSの教本）」を目指す上で、ランニングコストと法的・技術的リスクを極限まで下げる以下の設計方針を合意した。

### ① 徹底的な「0円運用」の原則
*   **有料APIの完全排除**: OpenAI等の従量課金APIを前提とせず、**「利用者が自分で取得した無料Gemini APIキー」**または**「完全無料のローカルLLM（Ollama等）」**をサポートする。
*   **無料インフラ**: DBは無料枠が手厚いSupabaseやNeonを前提とし、容量オーバーを防ぐ防衛設計を敷く。
*   **クライアントサイド完結**: PDF生成やデータ出力に有料SaaSを一切使わず、ブラウザ内ライブラリ（`jsPDF`等）で処理する。

### ② 認証トグル設計
個人利用（スタンドアロン）時に「ログイン画面」が邪魔になるのを避けるため、環境変数 `NEXT_PUBLIC_DISABLE_AUTH=true` の場合は、認証を完全にバイパスし、システム管理者としての仮想セッションを自動返却して即座に使える快適なUXを提供する。

### ③ 3大拡張インターフェースのCore定義
将来的にシステムが複雑化・高機能化しても、Coreのコードを書き換えずにプラグイン形式で機能差し替えができるよう、あらかじめ以下の窓口（Interface）を定義する。
1.  **`ILLMProvider`**: クラウドAI ⇄ ローカルAIの切り替え。
2.  **`IDataExporter / Importer`**: CSV ⇄ PDFなどのフォーマット拡張。
3.  **`INotificationProvider`**: 画面内通知 ⇄ Eメール/LINE/Slackへの通知先拡張。

## 3. GitHubリポジトリ ＆ フォルダ構成の選定

### 決定されたアプローチ：モノレポ（npm workspaces）構成
Git Submodulesによる複数リポジトリ管理は、利用者のクローン手順（`git clone --recursive`）やサブモジュールのハッシュ管理が複雑で、非プログラマーの導入ハードルになる。
そのため、**「1つの親リポジトリに、Core・スタンドアロン・プラグイン3種を独立フォルダとして内包し、npm workspacesで管理するモノレポ構成」**を採用した。

これにより、以下のメリットを同時に達成した。
*   `git clone` 一発で全員が即座に起動できる簡便性。
*   「BaseKit」という単一リポジトリへのGitHubスターの集中。
*   フォルダが物理分割されているため、依存関係がクリーンなままであることの証明。
